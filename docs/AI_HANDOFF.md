**Prior checkpoint task / slice:** Codex review remediation of `661796f` (statement-boundary grace classifier) — still authored-only, not executed against any database. TEST-01 disposal/TEST-02 provisioning status is unchanged this checkpoint; see below.

**Codex review of `661796f` and remediation (2026-08-17):** Codex found one Low issue, addressed this checkpoint; no Critical/High/Medium findings.

- **Low — sibling candidates for grace, and the "newly added" set itself, were derived relative to the platform baseline (minus whatever was already pending), not relative to the immediately preceding statement.** `assertPreFinalStatementBoundary` computed `newlyAdded` as "added vs. baseline, and not already in `pending`." An entry that failed grace at some earlier statement is a real violation, is reported once, and is correctly never added to `pending` — but it remains present in every later snapshot (nothing revoked it) and therefore remains present in the baseline-relative `added` set forever. Because it was never pending, it kept reappearing in `newlyAdded` at every later boundary, available both as a spurious "still not fixed" re-check and — the concrete risk Codex demonstrated — as a false correlated PUBLIC sibling if a later, unrelated statement happened to `CREATE OR REPLACE` the very same object: the stale rows would satisfy `isKnownCreationDefaultPrivilege`'s sibling/object-identity check and get waved into `pending` as if they were that statement's own fresh default, disappearing from that boundary's report. Codex's synthetic repro: an unrelated statement produces 3 immediate violations on function `q()`; a later, snapshot-unchanged `CREATE OR REPLACE FUNCTION q()` then re-grants grace to all 3 with 0 problems reported at that boundary. Fixed: `assertPreFinalStatementBoundary` now takes `previousSnapshot` (the actual snapshot immediately preceding the one being judged) and derives both the lingering-pending check's `newlyAdded`/sibling-candidate set from `diffAgainstBaseline(previousSnapshot, snapshot)` — genuinely new since the last statement — instead of "not already pending." `scripts/run-boundary-privilege-invariant.mjs`'s `assertStatementModeFile` already tracked a `previous` cursor per statement (previously used only for `assertExaminedGrowth`); it now also threads that same cursor into `assertPreFinalStatementBoundary` as `previousSnapshot`, including across its own file boundary (deliberately — see below), so no new bookkeeping was needed at the runner level.
- **Consequence for the existing per-file grace-reset test, addressed rather than left inconsistent:** with `previousSnapshot` now the real preceding snapshot (which spans file boundaries, unlike `pendingGrace`, which still resets per file by design), a privilege left open at one file's end is no longer "newly added" at the next file's first statement — it already existed before that file started. This is correct, not a regression: the entry was already reported once, at its true first appearance, and remains independently caught at every file boundary by the caller's own ungraced `assertPreFinalBoundary` (unchanged, proven by the neighboring test). Re-flagging it a second time inside the next file's internal statement check would itself have been the kind of memory-less re-reporting the "report once, at first appearance" design principle argues against. Updated the affected test's expectations and renamed it to state what it now actually proves (no `pendingGrace` leak across files, distinguished from a genuine leak's "adjacent" message) rather than the outdated "fresh immediate violation" framing.
- Added tests: the exact repro Codex described (unrelated-statement violation on `q()`, then a same-object `CREATE OR REPLACE` with an unchanged snapshot, asserting the old rows are not re-admitted to `pending`); and an explicit cross-object case (`CREATE FUNCTION y()` whose statement diff also contains an unrelated `PUBLIC` row on a different function `z()` and an `authenticated` row on `y()` with no correlated `PUBLIC` sibling for `y()`) asserting neither is graced.

The `public` row itself still graces unconditionally (it is the PostgreSQL-constant fact). Rewrote the comments to state the true distinction (which violation message comes back, not whether one comes back), renamed the test accordingly, and added an explicit control assertion that directly exercises `assertPreFinalStatementBoundary` with file one's actual leaked pending state to show it produces the "adjacent" message — then asserts the real `assertStatementModeFile` call for file two does not match it.

Anything else newly observed now fails immediately, at the boundary it first appears, rather than waiting a statement. `scripts/run-boundary-privilege-invariant.mjs` was updated to classify and pass the executed statement.
